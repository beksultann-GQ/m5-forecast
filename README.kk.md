# M5 Forecast — күнделікті сатылымды болжау

[M5 Forecasting Accuracy](https://www.kaggle.com/competitions/m5-forecasting-accuracy) деректеріндегі сұранысты болжаудың production-ready пайплайны.

> **Күйі: жұмыс істейтін жіңішке вертикаль.**
> Деректер қабаты, фичалар витринасы, baseline-дар және LightGBM оқыту жүзеге асырылған және тексерілген.
> `make demo` бәрін синтетикада ~20 секундта жинайды, Kaggle аккаунтысыз.
> Витринаға инференс, WRMSSE, MLflow Registry, Airflow тасктары және сыртқы деректер —

## Есептің қойылымы

Бұл жарыс емес, өнімдік есеп. Тұжырымдама код жазылғанға **дейін** бекітілген.

**Нені болжаймыз.** (тауар, дүкен) жұбы бойынша данамен күнделікті сатылым. Горизонт — 28 күн.
30 490 қатар: 3 049 тауар × АҚШ-тың 3 штатындағы (CA, TX, WI) 10 дүкен.

**Тұтынушы кім.** Шартты сатып алу бөлімі. Оған realtime API емес, жеткізушіге тапсырыс беру
цикліне сай аптасына бір рет батч-болжам керек. Барлық архитектуралық шешімдер осыдан шығады:
витринаға батч-инференс, FastAPI дайынды береді, модель жүріп жатқанда ештеңе есептемейді.

**Метрикалар.**

| Метрика | Рөлі |
|---|---|
| **WRMSSE** | Жарыс метрикасы. 12 агрегация деңгейі бойынша салмақталған. Ашық лидербордпен салыстырып, әлемде қай жерде тұрғанымызды түсіну үшін керек. |
| **WMAPE** | Бизнес-метрика. «Біз көлемнің 23%-ына қателесеміз» — бұл сатып алушыға түсінікті. MAPE қолданылмайды: мәндердің ~68%-ы нөл. |
| **Bias** | Жүйелі кем/артық болжау. Кем болжау = жоғалған сатылым, артық болжау = қатып қалған ақша және есептен шығару. Таңбасы модулінен маңыздырақ. |

**Жеңу керек baseline.** `seasonal_naive`: сатылым = дәл 28 күн бұрынғыдай.
Оған қоса `dow_mean` (8 апта ішіндегі апта күні бойынша орташа) — әділірек планка ретінде.

Baseline-сыз кез келген ML — карго-культ. Мұнда алынған сан — бүкіл жобаның планкасы.

## Архитектуралық шешімдер және неге дәл осылай

**Feature engineering SQL-де (DuckDB), Python — желім.**
Long-форматқа ашқаннан кейін бұл ~59 млн жол. Мұндай датасетте `pd.melt` ноутбукта
мүлде жұмыс істемейді. DuckDB `UNPIVOT` + терезелік функцияларды out-of-core орындайды.
Сонымен қатар бұл нақты DWH-та фичалардың қалай есептелетініне жақынырақ.

**Бір функция train үшін де, inference үшін де фичаларды есептейді.**
Екі скрипт емес. Айырмашылық тек `as_of` параметрінде. Әйтпесе
training/serving skew шығады — валидацияда бәрі тамаша, ал продта қоқыс болатын
классикалық прод-баг, себебі inference-скриптте біреу rolling mean-ді сәл басқаша есептеген.

**Барлық лагтар мен терезелер кемінде 28 күнге жылжытылған.**
Болжам горизонты — 28 күн. Демек, болжам сәтінде соңғы 28 күннің сатылымы
әлі белгісіз. `lag_7`-ні продта физикалық түрде есептеу мүмкін емес, ал валидацияда
ол керемет скор береді. Бұл қатарларды болжаудағы №1 қате, әрі ол үнсіз.

**Recursive емес, direct.** Recursive (1-күнді болжадық, фичаларға қойдық,
2-күнді болжадық) 28-күнге қарай болжамды толықтай дерлік өз болжамдарының
үстіне құрып, қатені жинақтайды. Мұнда горизонттың әр күні болжам сәтінде
белгілі фичалардан тікелей болжанады.

Дауыстап айтуға тұрарлық маңызды ескерту: **қазіргі фичалар жиынтығында горизонт
топтары (1-7, 8-14, ...) мағынасыз.** Барлық лагтар >= 28 және жол күніне
қатысты есептелетіндіктен, бір фича векторы бүкіл горизонт үшін жарамды —
төрт модель бірдей деректерде оқыр еді. Direct multi-step жақын горизонттарда
фичалар жаңарақ болғанда ақталады: h=1..7 үшін `lag_7` алу заңды.
Бұл SQL-де минималды лагты параметрлеуді және төрт витрина жинауды талап етеді —
бұл келесі қадам, әлі істелген нәрсе емес.

**LightGBM, objective=tweedie.**
Таргеттің ~68%-ы — нөлдер. Tweedie — Пуассон (қанша сатып алу) мен гамманың (сатып алу көлемі) қоспасы,
дәл үзік-үзік бөлшек сұраныстың құрылымы. M5-те RMSE-ні тұрақты жеңеді.

**Дүкен бойынша 10 модель.**
Пиктік жад азырақ (MacBook-қа сыяды), оған қоса модель дүкеннің ерекшелігін ұстайды.
Барлығы 10 × 4 = 40 шағын модельден тұратын ансамбль.

**Нейрожелілерге тимейміз.** Бүкіл пайплайн жұмыс істемейінше, N-BEATS және соған ұқсастар
жобаға құндылық қоспайды, ал уақыттан бір айды жейді.

## Қосымша дереккөздер

Kaggle-датасеттен бөлек екі сыртқы API қосылған. Екеуі де тегін, кілтсіз.

### Ауа райы — Open-Meteo (қосалқы нұсқа: Visual Crossing)

**Гипотеза.** Ауа райы сатылымды қозғайды: ыстық → сусындар мен балмұздақ, қар жауу → дүкенге
трафиктің құлауы, кенет суық → қорға сатып алу. FOODS үшін (M5-тің ең ірі
категориясы) әсер байқалуы тиіс.

**Нені аламыз.** Әр штатқа бір репрезентативті нүкте бойынша күнделікті агрегаттар
(LA / Даллас / Мэдисон). Walmart дүкендерінің нақты мекенжайларын жарияламайды —
бұл саналы жеңілдету, оны жасырмай, ашық айту керек.

**Туынды фичалар.** Шикі температура — әлсіз белгі. Жұмыс істейтіні — **нормадан ауытқу**:
Висконсиндегі қаңтардағы +25 °C және Калифорниядағы шілдедегі +25 °C мүлде басқа нәрсені білдіреді.
`temp_anomaly`, градус-күндер `hdd`/`cdd`, `is_heavy_rain` / `is_snow_day` жалаушалары,
`temp_change_1d` айырмасын есептейміз.

**Басты тұзақ — training/serving skew.**
Оқытуда нақты ауа райы белгілі. Инференсте 28 күндік горизонтқа —
белгісіз және белгілі болуы мүмкін емес. Стратегия:

```
1–16 күндер  →  Open-Meteo Forecast API болжамы
17–28 күндер →  жыл күні бойынша климаттық норма
```

`weather_source` бағаны (`archive` / `forecast` / `climatology`) витринаға дейін жетеді
және бөлек мониторингтеледі. Егер `climatology` үлесі секіріп кетсе — сыртқы API құлаған,
және алыс горизонттағы сапа факт келгенге дейін-ақ төмендейді.

Әділ нұсқа — бірден «болжамдық» ауа райында оқыту, бірақ бізде тарихи болжамдар жоқ.
Бұл жазылып қойған шектеу, ұмытылған деталь емес.

### Мемлекеттік мерекелер — Nager.Date

**`calendar.csv`-де `event_name_1/2` бар болса, неге керек:**

1. M5 оқиғалары — аймақтық белгісі жоқ жалпақ тізім. Cesar Chavez Day — Калифорнияда
   демалыс, ал Техаста қарапайым жұмыс күні. Nager мерекелерді субдивизиялар
   бойынша береді (`US-CA`, `US-TX`, `US-WI`).
2. Nager түрлерін ажыратады: Public / Bank / School / Optional — трафикке әсері әртүрлі.
3. Тәуелсіз дереккөз: салыстырып, M5-оқиғаларындағы олқылықтарды табуға болады
   (`m5 external compare-events` командасы).
4. **Ешқандай skew жоқ.** Ауа райынан айырмашылығы, мерекелер күнтізбесі жылдар бұрын белгілі
   және train-де де, продта да бірдей қолжетімді. Бұл «тегін» фича.

**Туынды фичалар.** Мереке күнінің өзі — әлсіз сигнал: дүкен жартылай бос немесе жабық.
Жұмыс істейтіні — маңайы: **алдыңғы күні** сатып алады. `is_day_before_holiday`,
`is_day_after_holiday`, `days_to_next_holiday`, `is_long_weekend` есептейміз.

### Бұның шынымен көмектескенін тексеру

Сыртқы деректер «салмақты көріну үшін» қосылмайды. Жобада ablation қарастырылған:

```bash
make backtest                       # база
m5 model backtest --ablation        # база / +ауа райы / +мерекелер / бәрі
```

Салыстыру бірдей фолдтарда жүреді. Егер өсім нөл болса — дереккөз алынып тасталады.
Бұл кестенің нәтижесі README-де жатуы тиіс: бұл «сыртқы деректерді неге алдың» деген
сұраққа жауап.

## Валидация

Ешқандай random split. Тек уақыт бойынша **rolling origin**.

```
|-------------- train --------------|--- gap 28 ---|--- val 28 ---|
                                   T                              T+56
```

**28 күндік gap міндетті.** Онсыз train шекарасында есептелген сырғымалы
статистикалар val-дан күндерді қамтып кетеді. `gap = horizon` болғанда мұндай
мүмкіндік құрылымы бойынша жоқ.

Соңғы күннен артқа қарай «баспалдақпен» 4 фолд, кеңейетін оқыту терезесі
(ескі тарих жылдық маусымдылықты алып жүреді — оны лақтырудың қажеті жоқ).

Бұған тесттер жазылған: [tests/test_leakage.py](tests/test_leakage.py). Негізгісі —
`test_feature_value_stable_when_future_changes`: `as_of`-тан кейінгі сатылымды өзгертеміз
де, `as_of`-қа дейінгі фичалардың байт-байтына өзгермегенін тексереміз. Өзгерсе —
қандай да бір фича болашаққа қарап тұр, қайсысы екені маңызды емес.

## DBeaver-де деректерді қарау

Файл жолы: `make dbpath`. DBeaver-де — **New Database Connection → DuckDB**,
жолды **Path**-қа қою.

*Driver properties* қойындысында `duckdb.read_only = true` қою **міндетті**.

Себебі: DuckDB — файлды құлыптайтын ендірілетін ДҚ. Бір мезгілде
**не жазуға бір процесс, не оқуға қанша болса да** мүмкін. Жазуға қосылған
DBeaver файлды ұстап тұрады — және пайплайн
`Could not set lock on file` қатесімен құлайды.

| Команда | Режим | DBeaver-мен (read-only) сыйысады ма |
|---|---|---|
| `make baseline`, `make train` | оқу | иә |
| `m5 db tables / peek / sql` | оқу | иә |
| `make staging`, `make features`, `make demo` | жазу | жоқ, Disconnect керек |

Оқыту кезінде витринаны қарауға болады. DBeaver қосылып тұрғанда оны
қайта жинауға — болмайды.

## Airflow

**`m5_training`** — апта сайын, жексенбі 02:00

```
ingest → validate → external → build_features → train → backtest
       → прод-модельмен салыстыру → тіркеу, ЕГЕР 1%+ жақсырақ болса
```

Соңғы қадам — гейт. Жаңа модель жаңа болғаны үшін ғана продқа кетпейді.
1%-дан аз ұтыс — фолдтар арасындағы шу, прогресс емес.

**`m5_inference`** — күн сайын, 05:00

```
registry-ден модель → фичалар → 28 күнге болжам
       → sanity-checks → витрина → нақты сапа + дрейф
```

Sanity-checks витринаға жазар **алдында**: NaN мен теріс мәндер жоқ, жолдар саны
`n_series × 28`-ге тең, көлем өткен 28 күннің фактісінен ±40% шегінде.
Жаман болжам болжамның жоқтығынан жаман — соның негізінде тауар сатып алады.

**`m5_external_ingest`** — күн сайын, 03:00

Бөлек DAG: сыртқы API-лар өз себептерімен құлайды, және олардың құлауы
оқытуды да, болжамды да құлатпауы тиіс — олар кешегі кешпен жұмыс істеп кетеді.

Барлық тасктар идемпотентті, ретрайлары және құлаған кезде алерттері бар.

## Жұмыс тәртібі

Қадамдарды кемелдікке дейін сызықты түрде жүрмеу керек. Алдымен — **1–2 аптада жіңішке вертикаль**:

```
деректерді жүктеу → 5 фича → LightGBM → бір метрика → бір DAG → бәрі Docker-де
```

Сапасы нашар болса да. Содан кейін әр қабатты тереңдету.

Әйтпесе feature engineering-те екі айға тұрып қалып,
ең құндысына — пайплайнға — жетпей қалу қаупі зор.

Бәріне шамамен: **аптасына 8–10 сағатта 6–10 апта.**

**Істелді:**

1. ✅ `data/` + staging SQL → DuckDB-де raw → stg, wide→long ашу
2. ✅ `features/build.py` + ft SQL → фичалар витринасы, әр жинаудан кейін ағып кетуді (leakage) тексеру
3. ✅ `evaluation/cv.py` → gap-пен rolling origin, фолд шекараларына тесттер
4. ✅ `models/baseline.py` → планка 4 фолдта бекітілді
5. ✅ `models/train.py` → дүкен бойынша LightGBM tweedie, baseline-ды жеңеді

**Әрі қарай басымдық бойынша:**

6. `evaluation/metrics.py::wrmsse` → жарыс метрикасы (қазір тек WMAPE/MAE)
7. `models/predict.py` → `mart.forecast`-қа инференс + sanity-checks
8. `evaluation/backtest.py` → тек нөлінші емес, барлық фолдтар бойынша жүргізу
9. `models/registry.py` → MLflow Registry және промоушен гейті
10. `external/` → ауа райы мен мерекелер + ablation, өсімді дәлелдеу
11. DAG-тар → `_beats_production` және `_sanity_checks` денелері
12. `monitoring/`, `serving/`, дашборд

## Әдетте қай жерде сынады

1. **Лагтар арқылы ағып кету (leakage).** Rolling mean-ді горизонтқа жылжытпай есептеді.
   Валидацияда скор керемет, тестте апат. `test_leakage.py` тесттерімен
   және «минималды лаг >= горизонт» ережесімен емделеді.
2. **Жад.** Бүкіл датасетте `pd.melt` жұмыс істемейді. DuckDB немесе Polars.
3. **WRMSSE.** Метрика тривиалды емес: 12 агрегация деңгейі, train-нің соңғы 28 күніндегі
   түсім бойынша салмақтар, RMSSE бөлімі тек train бойынша және тек алғашқы нөлдік емес
   сатылымнан бастап есептеледі. Көшіріп алмай, түсініп алу керек — әйтпесе
   сұхбатта түсіндіре алмайсың.
4. **Әлі сатылымда болмаған тауарлар.** Алғашқы сатылымға дейінгі нөлдер — бұл
   тауардың ассортиментте жоқтығы, нөлдік сұраныс емес. Оларды қиып тастау керек,
   әйтпесе модель қоқыста оқиды.
5. **Инференстегі ауа райы.** Сыртқы деректер бөлімін қараңыз: 28 күн алға нақты
   ауа райы жоқ. Мұны ескермесе, бэктест продта болмайтын жақсартуды
   көрсетеді.
