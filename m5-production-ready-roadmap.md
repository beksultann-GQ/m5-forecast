# M5 Forecasting Accuracy — production-ready проект

Пошаговый план: как превратить Kaggle-соревнование в проект, максимально приближенный к реальной работе.

**Источник данных:** https://www.kaggle.com/competitions/m5-forecasting-accuracy/overview

---

## Главное, что надо понять с самого начала

Production-ready ≠ высокий скор на Kaggle. Для рекрутёра или тимлида ценность проекта в другом: **воспроизводимость, автоматизация, тесты, мониторинг**. Модель может быть простым LightGBM — если вокруг неё нормальный пайплайн, это сильнее, чем пять ноутбуков с ансамблем.

Важный момент: сильный SQL и Airflow — это не недостаток на фоне слабого Python, а угол атаки. Feature engineering делаем на **DuckDB + SQL**, Python используем как клей. Так и честнее к своим навыкам, и в реальном проде часто делают именно так.

## Шаг 0. Определить задачу как продуктовую, а не соревновательную

Записать в README **до** всякого кода:

- **Что прогнозируем:** дневные продажи по паре (item, store), горизонт 28 дней.
- **Кто потребитель:** условный отдел закупок → нужен батч-прогноз раз в неделю, а не realtime API.
- **Метрика:** WRMSSE (метрика соревнования) + понятная бизнесу WMAPE/MAE.
- **Baseline, который надо побить:** seasonal naive (продажи как 28 дней назад).

Без baseline любой ML — карго-культ. Это первое, что спросят на собеседовании.

## Шаг 2. Слой данных

**Файлы M5:** `calendar.csv`, `sell_prices.csv`, `sales_train_evaluation.csv`, `sample_submission.csv`.

Данные лежат в широком формате (колонки `d_1 … d_1941`). После разворота в long-формат это ~59 млн строк — pandas на MacBook Air такое не потянет.

**Что делать:**

1. Скачивать через `kaggle` CLI скриптом (`make download`), не руками.
2. Сразу конвертировать CSV → **Parquet**, положить в `data/raw/` как immutable-слой.
3. Разворот в long и все джойны делать в **DuckDB** — это `UNPIVOT` + `JOIN` на SQL, работает out-of-core.
4. Слои назвать как в DWH: `raw → staging → features → mart`.

**Чек-лист:**

- [ ] Конвертация в Parquet
- [ ] DuckDB-трансформация wide → long
- [ ] Слои raw/staging/features/mart разделены

## Шаг 4. Стратегия валидации — самый важный шаг

Здесь ошибается большинство, и здесь легче всего выделиться.

- Никакого случайного train/test split. Только **rolling origin** по времени.
- 3–4 фолда: обучение до дня T, прогноз на T+1…T+28.
- Между train и val обязателен **gap в 28 дней**, иначе лаги протекут.
- Все фичи считаются только по данным, доступным на момент T.

Написать на это юнит-тест: проверяет, что `max(date)` в train < `min(date)` в val. Тест на утечку в pet-проекте — сильный сигнал.

**Чек-лист:**
- [ ] Rolling origin CV реализован
- [ ] Gap в 28 дней соблюдён
- [ ] Тест на утечку написан и проходит

## Шаг 5. Фичи (на SQL)

Ядро задачи. Минимальный набор:

- **Лаги** продаж: 28, 35, 42, 56, 364.
- **Скользящие статистики** (mean / std / max) по окнам 7 / 28 / 180 — обязательно со сдвигом на 28 дней.
- **Календарь:** день недели, месяц, номер недели, праздники (`event_name_1/2`), **SNAP-дни** по штатам (дни выплат пособий — сильно двигают продажи еды).
- **Цены:** текущая цена, изменение к прошлой неделе, отношение к средней по товару, момент первого появления цены.
- **Иерархия:** `item_id`, `dept_id`, `cat_id`, `store_id`, `state_id`.

Всё это — оконные функции, `LAG` / `AVG OVER`.

> **Ключевое требование production-ready:** одна и та же функция считает фичи для train и для inference. Не два разных скрипта. Иначе получится training/serving skew — классический прод-баг. Упомянуть это в README полезно.

## Шаг 6. Модель

- **LightGBM**, objective **`tweedie`** (`variance_power` ≈ 1.1) — данные сильно разрежены, много нулей; Tweedie на M5 работает заметно лучше RMSE.
- Схема: **direct multi-step** — отдельная модель на каждый горизонт либо на группы горизонтов (1–7, 8–14, 15–21, 22–28). Recursive накапливает ошибку.
- Разбивать обучение по магазинам (10 моделей) — меньше памяти, лучше качество.
- Все гиперпараметры — в yaml-конфиг, ничего не хардкодить.

Нейросети (N-BEATS и подобные) не трогать, пока не работает весь пайплайн. Ценности проекту они не добавят, а времени съедят месяц.

**Чек-лист:**
- [ ] LightGBM + tweedie обучается
- [ ] Direct multi-step по группам горизонтов
- [ ] Гиперпараметры вынесены в конфиг
- [ ] Baseline побит

## Шаг 8. Оркестрация (Airflow)

**DAG `m5_training`** (еженедельно):

```
ingest → validate → build_features → train → backtest
       → сравнить с прод-моделью → зарегистрировать, если лучше
```

**DAG `m5_inference`** (ежедневно):

```
забрать модель из registry → посчитать фичи → предсказать на 28 дней
       → записать в витрину → sanity-checks
```

Sanity-checks: нет отрицательных значений, нет NaN, объём прогноза в разумных пределах.

Обязательно: идемпотентные таски, retries, SLA, алерты на падение.

**Чек-лист:**
- [ ] DAG обучения
- [ ] DAG инференса
- [ ] Идемпотентность и retries
- [ ] Алерты настроены

## Шаг 9. Мониторинг

- **Data drift** — распределение фичей vs обучающая выборка (**Evidently** делает это из коробки).
- **Prediction drift** — среднее и разброс прогнозов.
- **Качество по факту** — когда приходят реальные продажи, считать MAE/WMAPE за прошлые 28 дней и складывать в таблицу.
- **Дашборд** — Streamlit или Grafana.
- **Алерт** — если ошибка выросла на X%, триггерить переобучение.

## Шаг 10. CI/CD и упаковка

- **pytest:** тесты на фичи (лаг реально сдвигает), на метрику (WRMSSE на синтетике), на схему данных.

## Порядок работы

Не идти по шагам линейно до совершенства. Сначала сделать **тонкую вертикаль за 1–2 недели**:

```
скачать данные → 5 фичей → LightGBM → одна метрика → один Airflow DAG → всё в Docker
```

Даже с плохим качеством. Потом углублять каждый слой.

Иначе большой риск застрять на feature engineering на два месяца и не дойти до самого ценного — пайплайна.

Ориентировочно на всё: **6–10 недель при 8–10 часах в неделю.**

## Где обычно ломаются

1. **Утечка через лаги** — посчитал rolling mean без сдвига на горизонт. Скор на валидации великолепный, на тесте катастрофа.
2. **Память** — `pd.melt` на всём датасете не работает. DuckDB или Polars.
3. **WRMSSE** — метрика нетривиальная (взвешенная по 12 уровням агрегации). Взять готовую реализацию с Kaggle, но разобраться, как она устроена, иначе не объяснить на собеседовании.
4. **Товары, которых ещё не было в продаже** — нули до первой продажи это не спрос, а отсутствие товара. Их надо отрезать, иначе модель учится на мусоре.
